# Rule claims, and how rules share code

The game is fully programmable only if every line of game code answers to a rule. So every function claims the rule
(or clause) whose text it carries out, and no rule edits another rule's code.

## The convention

A JSDoc tag directly above the function:

```ts
/** You move only onto a charted tile no other piece stands on. @rule 504, 202 */
actionAllowed(ctx, actor, action) { ... }
```

- `@rule <number>` names a rule (`504`), a clause (`504.1`) or a block (`500`) that exists in the game's `RULES.md`.
  One tag may list several, separated by commas or spaces; there may be several tags.
- It goes on every function: declarations, `const f = (...) =>`, methods (hooks), route handlers. A callback passed
  inline (`.map((x) => ...)`) belongs to the function around it.
- Site plumbing with no rule of its own (the engine's helpers, routing, sign-in, email) goes under **101** (follow the
  rules) or **102** (players) for now. `docs/rules-reorg.md` retires 302 and gave the site's own code rules 102 to 110 (110 retired 2026-11-20);
  tags move to those numbers when that text lands, in the step PRs. A function claimed by more than 3 rules is reported
  as a warning: it probably does several jobs.
- Rule numbers follow `docs/rules-reorg.md`: the modules claim `202.2` (the turn's parts, once a day for the move),
  `504.1` (charting) and `504.2` (where you may move), which is why the starter `RULES.md` and Rickshaw's now carry those
  clause markers. Nothing else in the text was reworded.

## What is checked, and where

| Where | Checked by | A missing or unknown tag |
|---|---|---|
| `src/engine/`, `templates/rules/*.ts` | `node scripts/check-rule-claims.mjs` (first step of `npm test`), against `templates/RULES.md` | fails |
| a game's `rules/<n>.ts` | `scripts/bundle-games.mjs` on every build, against that game's `RULES.md` | fails the build |
| the rest of `src/` (routes, lib, index) | the same script, report only | listed in `docs/rule-claims-todo.md` (regenerated by `npm test`); a follow-up claims them and moves `src/` into the strict set |

The checker is a line scan (`src/engine/claims.js`), not a parser. It finds declarations, `const f = () =>`, `name: () =>` and `name(...) {` on one line; only a `/** */` block counts. For rule modules the build also asks the LOADED module for its hooks and fails unless each is a tagged function the scan can see, so an odd shape fails closed. A named helper needs its own tag wherever it sits; an inline callback belongs to its function.

## The map the rule cards will read

The bundle (`src/generated/games.ts`) carries, for each game and for the starter pack, `claims`
(`{"504": ["rules/504.ts#actionAllowed", "rules/504.ts#afterAction"], ...}`), and `ENGINE_CLAIMS` for `src/engine/`
(`{"505": ["src/engine/hooks.js#spawnTile", "src/engine/host.ts#chooseSpawn"], ...}`). Per game there is also
`worksWith`: for each rule and hook, the other rules that implement the same hook
(`{"202": {"actionAllowed": [504]}}`). No UI uses them yet.

## How several rules share one place in the code

Rules never edit each other's code. A rule's module registers its own handler for each hook it cares about, and the
engine calls every handler. Each hook has one combine mode (`src/engine/hooks.js`, `HOOKS`):

| Mode | For | What happens |
|---|---|---|
| `veto` | can-I hooks (`actionAllowed`) | every handler runs in rule-number order; any may refuse, with a reason naming its rule; the first refusal wins |
| `sequence` | effect hooks (`afterAction`, later `onEnacted`, `dayEnd`) | every handler runs in rule-number order; their effects are joined in that order |
| `decide` | single-value hooks (`spawnTile`, later `voteMark`, `tally` ...) | one handler decides. Two handlers fail the build today: the lowest rule number winning is NOT built, because it waits for a precedence rule Buster has to approve |

So rule 504 adding a charting effect, or a new rule 506 adding a move restriction, changes no existing file: it adds a
module. A proposal that breaks a hook shows up as that rule's own failing test, never as a quiet change to another rule.
