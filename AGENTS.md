# AGENTS.md — working on Promptocracy

Read this before changing anything here. It holds the decisions and conventions that aren't obvious from the code. `CLAUDE.md` imports it.

## What this is

Promptocracy is a self-amending game (after Peter Suber's Nomic) at promptocracy.us. This repo is the **platform**: one Cloudflare Worker + D1 database hosting many games. Each game has its own public GitHub repo holding its rules (first one: `busterbenson/promptocracy-rickshaw`, Rickshaw Game 1). Chalant, the AI, is the game's **moderator** (never "referee").

Owner: Buster Benson. He decides game design; agents build what he approved.

## Hard rules for anyone working here

1. **Don't invent mechanics.** The game grows through play. If a build needs a mechanic that isn't decided, stop and ask (with a lean). Don't add claiming, terrain, harvesting, tile properties, etc. by default.
2. **The rules are the game.** Every rule change ships as rule text + enforcing code + tests, together. Never add rule text before the PR that implements it; never add behaviour no rule states. Rules that need judgment call a small model (Haiku/Jev/Flash) behind a test with recorded answers.
3. **Every engine function is claimed by a rule.** Tag it `@rule <n>` (JSDoc). `scripts/check-rule-claims.mjs` (in `npm test`) fails on unclaimed engine code or a tag naming a rule that doesn't exist. Site plumbing (sign-in, email, DB) is claimed by 302 / 102. Repealing a rule means its code is removed or reassigned in the same change.
4. **No helper text, anywhere.** No intro paragraphs, captions, eyebrow labels, hint lines, "how this works" asides, reward reminders ("+10 if it passes"), restated rules ("One proposal a day") or "log in to…" nudges. What the UI shows is labels, data, state, and a reason next to a disabled control. If it matters to play, it's a rule: point at it with a rule pill. (Buster, 2026-11-20: "Just have a general rule against random helper text.") Mockup copy that breaks this rule is not built, even when a checklist line asks for it.
5. **Vocabulary:** moderator (not referee); players "join the game" (not "take a seat"); creatures (hostile / neutral), Blob, Ghost, Crow; "Use this piece" / "Change your piece"; "You" for the center-on-my-piece button.
6. **One helper, one window** (Buster, 2026-11-24: "remove starling for now and have gremlin do all of it. In his grumpy gremlin voice."). Gremlin is the only chat agent. His window (`createChat`, `public/js/chat.js`) is on every page of the game for a signed-in player: header, the row under it (`.ch-row`, the strip "Yours": your proposals not yet voted on (P-pills: drafts of today and locked in, drafts first then newest; a tap shows that proposal's slip in the general conversation) and your tickets not yet voted on (W-pills: a tap opens that ticket's conversation), then "+ New"; in the general conversation a second row, Today: "P13 P14  n of 3 left"), log, composer, cap counter, minimize/close. He has two kinds of conversation (rule 801.6): the **general conversation** (`chat_messages.ticket_id IS NULL`), where rule changes and actions are drafted through the one drafter (`draft` in `src/routes/api-proposals.ts`, every check it has stays; `prepareDraft` is its drafting half) and shown as a slip (Lock it in primary, Unlock, the day's count), and rule questions are answered with checked quotes; and **one conversation per ticket**, where a commission is drafted and shown as a slip (the drawing of each entry with Redraw, which costs one of his messages like the card's, and Lock it in / Unlock like the general slip; a lock-in from the Workshop card closes the card and lands in this conversation, and a card closes on the phone's back gesture). The player never picks: he works out the kind, and when a message belongs in the other conversation the site moves it there in the same request (`commission` in his general answer opens a ticket; `move: "general"` in a ticket answer takes the message out), at most once a turn, one message counted. His two answers have two schemas (`generalSchema` in `src/lib/gremlin-rules.js`, `answerSchema` in `src/lib/gremlin.js`: the ticket's is at the live-verified size, 30 properties); one persona (`personaText`). **No dead ends**: every turn ends with a draft or two or three concrete `options`, a rule change is drafted at once with the guesses named in one line, and an escalation is never the whole reply. The old Starling endpoint answers 410. Anything that changes in his window ships for both conversations in the same PR, and `tests/browser-chat.py` holds the row checks (same height, same place), the strip's P- and W-pills, and that the window is in the same place on every tab of the board (Summary, Rulebook, Workshop, History, Yours) at 1280 and 390. The board is the only page a signed-in player plays on (`public/board.html`; the landing, join, log-in and 404 pages are for visitors), so a new page that a player can be on gets the same window.

## Architecture (decided 2026-11-19; detail in docs/step1-plan.md)

- **The game's repo is the game.** Per rule: text in `RULES.md`, code in `rules/<n>.ts` (handlers for engine hooks), tests in `rules/<n>.test.ts`. Settings (`[setting: key]`) are data in `settings.json`, no code.
- **Bundled at deploy.** A Worker can't load code at runtime, so the build fetches each game repo at its latest `day-N` tag, validates it (manifest, allowed paths, lint: no network calls, no imports beyond the engine API), runs its tests, and bundles text + settings + modules. The rulebook served is the bundled text, so it always matches the running code.
- **Shared, dumb engine.** It runs the day loop and calls hooks. Rules never edit each other's code; each registers handlers. Combine modes: `veto` for can-I hooks (any rule may refuse, with a reason naming its rule), `sequence` for effects (rule-number order), `decide` for single values (precedence rule picks; lower number wins). A capability the engine lacks gets a new hook for all games, separately from the rule that needs it. A function claimed by more than 3 rules is a smell: split it into hooks.
- **The moderator** may only touch a game repo's `RULES.md`, `settings.json`, `catalog.json`, `rules/`, `rulings/`. It runs on Buster's Mac mini (headless Claude Code via launchd), not in the Worker.

## The day (decided 2026-11-19)

- Days run midnight to midnight in the game's time zone. **No early close.**
- **Midnight lock:** from midnight until the previous day is processed, the game is locked on web, API and MCP (no moves, votes, proposals, End turn). Every write route checks the clock itself, not only the cron's flag. The page says the moderator is processing day N.
- A turn: move one space (or change your piece's shape instead), propose up to 3 changes (setting `proposals.per_day`, rule 103.2), vote on each proposal. **End turn is final**; votes can change and a proposal can be withdrawn until midnight or until you End turn.
- Votes are hidden until midnight. Votes are counted among the players who voted (104.1, Buster 2026-11-24): majority = more than half of them yes, unanimous = every one of them yes, nobody voting fails; **not voting counts neither for nor against**, and the Champion's change is counted by 402.4. The electorate is fixed at the start of the day; a proposal's mark is stored at confirm, the number it needed only at the count.
- Proposals: reword a rule or one clause (scope step: whole rule vs clause), add a clause, add a rule (pick a block), repeal, move, lock/unlock (unanimity mark); catalog proposals come with step 3. Code drafts mechanical changes; a small model (Haiku) drafts rewording. The vote mark is stored at confirm.
- **Midnight processing:** count votes (code), roll proposals, apply each passed proposal in order as one commit (text + code + tests) in the game repo, tests must pass, tag `day-N`, deploy, unlock when the deployed version matches. Points (401) when a change takes effect.
- **Failures:** each rule implementation has its own budget (time + effort, a setting). Over budget, or not done by **3:00 am** (rule 107.6, `DEADLINE_HOUR` in `src/lib/day-gate.js`; the changes must then be live by 4:00), = "not applied", no points, and the proposal goes **back to its owner with the moderator's reason and a suggestion** (split it, simplify it). Two rules that can't both hold: the core (unanimous) one prevails over a majority one, otherwise the **older** one prevails; the other goes back with reasons (a core meta rule).

## Rule text decisions

- 600 (hearts + creatures) and 700 (making things) are **starter rules**, but their text enters a game's RULES.md in the step that ships their code (step 2, step 3).
- Death, Ghosts and the ending (Buster, 2026-11-22; replaces the old 601.4 Ghost / 601.5 moon bullets, no moons): 3 hearts (601), hostile creatures appear on nights nothing was applied, chase and bite (602), 0 hearts = dead: no vote, no turn, the piece lies where it fell (603.1); a living player next to it can give a heart to revive them before the Ghost rises (603.4: giver keeps 1, once a day, free of the move); after 3 days (`death.ghost_days`) they rise as a **Ghost** (603.3, 604): the same turn checklist, Move and End turn kept, Vote and Propose off, its piece replaces the player's and can't be changed, its moves chart tiles. The game ends by rule 404 (below). Rule text is in Rickshaw's RULES.md and `templates/RULES.md`; the engine side is the `night` and `ending` hooks (`src/engine/board-night.js`, `host.ts` nightBoardStatements), migration 0019.
- The 29 approved additions/rewordings are in `docs/rules-parity.md` (give-a-heart limits, 501.4 adjacency = 8 neighbours, End turn vs 104.3, …). Their numbers follow the approved **reorganization** in `docs/rules-reorg.md`: block 100 = rules about rules + everything the shared site does (103 Proposals, 107 The night, 108 When rules conflict, 109 Numbers and settings; 110 was retired 2026-11-20, see below); blocks 200+ = what each game's own rule code does; 302 retired. Use the reorg numbers in rule text and `@rule` tags.
- **Three levels, no text under a title (Buster, 2026-11-21; rule 109.1).** A block holds rules, a rule is its title and its numbered clauses, a clause holds the text. A rule has no text of its own: the ten that did (101, 201, 204, 301, 401, 403, 501, 502, 503, 505) state it as clause N.1, and a new rule's text is its N.1 (the drafter numbers it). Citing a rule cites all its clauses. A rule's clauses run N.1..N.n **with no gaps before day 1**; once play starts a repealed clause leaves its number empty and nothing renumbers. `checkRulebook` (`src/engine/rulesmd.js`, run by the bundler and every game's rulebook test) fails text under a title and a citation of a block, rule or clause that doesn't exist, always; the no-gap check runs only with `beforeDayOne` (the bundler passes it for a game whose latest tag is day-0.K; the platform test passes it for the template). 109.2 is the settings clause. "Say each thing once" is **guidance, not a rule** (`docs/rules-voice.md` 8, Gremlin's and the drafter's prompts, `moderator/APPLY.md`, `moderator/RULING.md`): nothing rejects a restatement.
- **Marks are on rules, never on blocks (Buster, 2026-11-21; rules 105.1, 105.2).** Every rule heading ends in `[u]` (unanimous) or `[m]` (majority) and a block heading has none; `checkRulebook` fails a rule without a mark and a block with one. Majority is what anything unspecified is. A proposal that adds a rule makes it majority unless the proposal marks it unanimous (the draft's `mark`, kept on the draft row until confirm; Gremlin's `add` takes `mark: "unanimous"`), and then it needs every player; a move keeps the rule's own mark; "mark" proposals are on a rule, not a block. The Era's winning score is the setting `eras.points_to_win` (rule 402.2), read by `rules/402.ts`.
- **Renumbering is free until the first game officially starts** (Buster, 2026-11-19): moving and renumbering rules for better organization needs no proposal before Rickshaw Game 1 starts. After that, renumbering is a "move" proposal like any other.

## Game design decisions (Buster, 2026-11-20)

- **No untouchable rules.** Rule 110 ("What no proposal can change") retires. Its 8 items (sign-in, midnight-to-midnight days, the daily proposal limit, End turn, hidden votes, votes counted by code, the lock, the deadline) become ordinary rules with a **unanimous** mark, each in its own block. Each moves behind an engine hook a game rule controls, the way 107 controls the night's order. Until an item's hook ships, a proposal on it is refused at drafting with the reason "not wired yet"; it never passes and does nothing.
  - **Status (2026-11-20): rule 110 is gone from the template and from Rickshaw.** All 8 items are still platform-run, so none has its hook yet: each is on `NOT_WIRED` in `src/lib/proposals.js` (102.4 sign-in, 103.2, 104.4, 104.5, 107.1, 107.6, 202.4, 203.1) and rule 103.6 (which states the restriction and lists the parts, itself included; 103.5, 103.7 and 103.8 are the action rules) says a proposal that changes one is refused at drafting, "Not wired yet: rule N", with no P-number. A reword that keeps the text and only sets a setting (`proposals.per_day`, `game.timezone`) still drafts: settings are data the site reads. A part leaves the list, and 103.6, in the PR that ships its hook: that PR edits `NOT_WIRED`, `templates/RULES.md` and the game's `RULES.md` together (once a game is live the game-side edit is a direct commit by the moderator's operator, since a proposal cannot change a not-wired part); the platform test pins the template's 103.6 to `NOT_WIRED` and each game's rulebook test pins its own. A draft that would conflict with a not-wired part (a repeal or move that leaves it citing nothing, or a conflict the model names) is refused too. Marks are per rule: 202 and 203 carry `[u]` as a whole (their other clauses, move distance and the time-zone setting, now need everyone), and so does every rule of the old block 100.
- **Eras** (built: rule 402, migration 0011). Winning an Era makes you Champion. The Champion names the next Era and can change one rule without a vote, a unanimous-mark rule included. The change passes **unless every other living player votes against it; not voting does not count as against** (the one place that differs from "not voting counts as no").
- **How the game ends (rule 404, Buster 2026-11-22).** No survival win. Three endings: **Paradox** (the only one with a winner; a moderator ruling names a living player, 403.1, 404.2), **Last one standing** (a night's deaths leave one living player: nobody wins, they are the King of Ghosts, 404.3) and **Everyone dead** (404.4; the last two dying the same night count as this, checked once at the end of the night after every bite). Ghosts and creatures are not alive. Ending sets `games.status = 'over'` plus `ending`, `ended_day`, `ending_player_id` (src/lib/end.ts); the existing gates then stop everything and `finalizeDay` opens no next day.
- **Ready commissions: hold, resume, cancel (Buster, 2026-11-25; rules 801.4, 801.9, 801.10).** "Players should choose to pay for a commission" and "If something passes and it can be afforded and started the same night, let's start building it immediately. If not, move it to ready state and let the user toggle it from ready to on hold if they want to prioritize other things the next night." A commission its owner can pay is paid at the count and joins the queue (unchanged). One they can't pay is Ready and paid on the first night they can (803.1), unless they put it on hold: the night skips it and the points stay theirs; taking it off hold makes it Ready again (it keeps its place in the order paid). They can also cancel it while Ready or on hold: nothing is paid, it closes as Shelved. "On hold" is not a stored state (`tickets.state` keeps its CHECK): it is Ready with `tickets.held_at` set (migration 0022), and the view shows it as On hold. The three actions are stopped by the midnight lock only (not End turn, and not a death: a dead player or a Ghost can still hold or cancel their own ticket). A cancelled ticket stays public, so does its page; its saved drawings are swept 30 days after the cancel like any Shelved ticket's (`src/lib/art-sweep.ts`).
- **Entries on the way (Buster, 2026-11-26; rules 701.4, 703.2, 703.4, 801.6).** "It should pass and be applied even if all the objects don't exist yet. It just has nothing to act on until the item exists." Gremlin sees the catalog's entries and what each open commission makes in BOTH conversations, the rule check (103.9: such an entry is not "missing"), the escalation answers and the night (`src/lib/pending-entries.ts` reads them, `src/lib/entries.js` is the pure part). Open = Proposed, Ready, On hold, Approved, Building, plus the viewer's own Draft (others' drafts are private). A ticket's `makes` has a third kind, `uses` (`{kind: "uses", name, catalogKind, num: "W4" | "C1"}`; `num` is reused so the ticket answer schema stays at 30 properties): it costs nothing, makes nothing and does not count as something to make (801.3). A duplicate entry (same kind and name, case folded) is saved, named to him next turn, and refused at lock-in with "W4 already makes an item called Flower (701.4). Use it or rename yours." (only in a rulebook that has 701.4). A general-conversation draft records what it uses (`proposals.uses`, migration 0024; a label "Uses Flower from W4", never a blocker). Rule code finds an entry by `entryMadeBy(ctx.catalog, "W4", "item")` (engine API; `ctx.catalog` entries carry `name` and `madeBy`), and does nothing while there is none. A making ticket that ends Refused, Failed or Shelved changes nothing automatic. Step 3's build (the moderator's half, `moderator/process-day.mjs` `catalogWith`) adds nothing to `catalog.json` for a `uses` item, and when a ticket that passed still makes a duplicate, it uses the existing entry instead of failing `readCatalog` (Buster's yes, 2026-11-26, with the night-builder plan).
- **An entry with no kept drawing keeps its newest (Buster, 2026-11-27; rule 801.2).** "For any catalog item without a saved drawing, assume the newest drawing is the saved one." It is done when the ticket leaves Draft (`keepNewest` in `src/lib/art.ts`, through the same `save`: saved, default, copied to `art/`, because `tmp/` goes after 30 days and only saved drawings are shown to others, built and swept). A drawing whose `tmp/` copy is gone is skipped for the next newest. Tickets that left Draft before it: `scripts/keep-newest-drawings.mjs <slug> [--apply]` (dry run by default; calls the moderator routes `unkept-drawings` and `keep-drawings`).
- **Items players hold and give (Buster, 2026-11-27; rule 704.1, migration 0027).** "Giving a flower loses a flower." A player holds catalog items (`player_items`: a count per player and item, never below 0, public on `/api/game` as `items`, shown as a "Holds" row on the card). A give MOVES one: the giver's count goes down by 1, the receiver's up by 1, in one guarded D1 batch (`src/routes/api-give-item.ts`; two gives racing for one holding: one lands, the other is a 409). The game's rules decide who may and when through the `giveItem(ctx, giver, target, entry)` hook (opt-in; `undefined` = the rule says nothing about that item, `null` = allowed, a refusal refuses; a give needs one allow and no refusal; the engine adds "You have no Flower." for a giver who holds none). `ctx.players[i].items` is what they hold, `ctx.turn.given` what the acting player gave today (read from `item_moves`, the record of gives and grants). Who starts with an item is not a rule: the operator grants it once (`scripts/grant-items.mjs <slug> <entry> <count> [--grant <id>] [--apply]`, dry run by default, one History line per player, a grant id so a second run grants nobody; the moderator route `grant-items`). A rule can hand a player an item with the `grant` effect (`effects.grant(player, entry, count)`), applied from `afterAction` (a move can pick something up); not from `night` yet. Not built: taking, dropping, trading or using items; items on the board.
- **Built entries are placed; structures; owners; protected bites (Buster, 2026-11-27, W2 Pancake and W6 House).** "Place Pancake and house in random spots on the board like a creature spawn. That is the default if not otherwise specified." A creature or structure that is built is placed once, the night it is built, at random on an unoccupied charted tile (a structure: every tile of its footprint), unless a rule says where or that it isn't placed: rule 701.5, the `placement` hook, `placeBuilt` in `src/engine/host.ts`. "Its owner" is the commission's requester (`entry.requester`, never in the public repo); a creature's drawing on the board is chosen by a rule (`creatureDrawing`); a rule can protect a player from a bite (`biteAllowed`, asked through `ctx.mayBite`). Buster's ask the same morning: build engine powers as modules. **Each is a capability in `src/engine/capabilities/` (registry in `index.js`; how to add one: `docs/capabilities.md`).** Its one-line sentence is read by Gremlin's rule check and written into `moderator/APPLY.md` and `moderator/BUILD.md` by `scripts/sync-capabilities.mjs`; `tests/capabilities.mjs` fails when any is missing.
- **The night's rules run in sequence (Buster, 2026-11-27, rule 602.6).** "Can you make all creatures do their moves in sequence so that they cannot occupy the same spaces?" The `night` rules (602 hostile creatures, 603 death, 606 Pancake ...) run one at a time, lowest rule number first, and each is given the ctx AFTER the earlier rules' effects: creature steps, appearances (with their ids, `nextCreatureId` moves on), players' moves, bites and deaths, creatures gone, structures placed (`rules.night(ctx, info, after)` in `src/engine/hooks.js`; `createBoard` / `runNight` in `src/engine/board-night.js`; `nightBoardStatements` in `host.ts`). The effects go onto ONE in-memory board in that order, so the batch (History, ids, the BOARD_OPEN guards) is the same as applying the joined list once; `applyBoard` is `createBoard` plus one `apply`. `resting` is not changed within the night (a creature that rests tonight rests the NEXT night, 602.5). The `step_refused` / `move_refused` backstop in the board stays. Not gated like placement: 504.2 and 602.2 already say a piece never moves onto a tile another stands on, so this makes the engine do what the text says; clause 602.6 (in `templates/RULES.md`, drafted for Rickshaw's) says it in words. A game's own tests still call `rules.night(ctx, info)` with no callback, where every rule sees the one ctx. Tests: `tests/night-sequence.mjs`, the night 5 case in `tests/move.mjs` (fixture rule 606 Follow).
- **Action proposals: yes**, as a fixed catalog of coded action types (resurrect, grant, move...). The vote needed is the stricter of the action's own mark and the strictest rule it touches; no override; recorded in History. Core rule 103.5: an action can only do what the game's rules already allow. Adding an action type is a rule change.

## Build plan

Step 1 (the day loop) is 8 PRs, in order, in `docs/step1-plan.md` section 7. Then step 2 (600), step 3 (700). Planning and the tricky parts (midnight processing, the lock, migrations, rules-as-code) use Opus; implementation and review use Sonnet; Codex reviews every PR.

**Step 3, the night builder (rules 803.2-803.4; Buster, 2026-11-26: "Build as much as you can each night. Deliver things early if you can. Only take longer if you run out of time each night.").** There is no due night: `estimate` never delays a build, and every paid ticket is built every night, in queue order, until the night's time runs out. **The Worker's half is built** (`src/lib/builds.js`, migration 0025): at the count every Approved ticket goes Building and the day goes to processing even with no rule change; `GET pending` lists `builds` (every Building ticket in queue order, with the ticket as voted, its kept and default drawings and its failures); the claim takes one outcome per Building ticket (built, failed with a reason, no_time, needs_engine with a one-line note) and refuses one for a ticket that isn't Building; once the deploy is live, built is Done, a failure counts and the 3rd makes it Failed (back to its requester with the reason; what was paid stays paid), and no time or waiting on the engine stays Building and is not a failure. A night that ends without the deploy leaves each build "not built tonight", no failure. Each change writes its History line (events, phase night, and `ticket_log`). **All of it is dormant until a game's rulebook has 803.2** (`builderOn` in `src/lib/day.ts`, the 701.4 / 103.9 pattern): 803.2-803.4 are in `templates/RULES.md` (so starter games build), not in Rickshaw's. **The moderator's half is built** (`moderator/process-day.mjs`, after the proposals): each listed ticket in queue order, with a proposal's budget (`night.apply_minutes`) cut to the night's time left (out of time = no_time). Its entries go into `catalog.json` by plain code (`catalogWith`: the next free id per kind letter in queue order, `madeBy`, `day`, the kept drawings and the picked default; a `uses` item adds nothing; a duplicate is the entry already there). Its rule items go through one `claude -p` call (`moderator/BUILD.md`, the APPLY.md sandbox, 2 fixes): the voted draft word for word, numbered and placed by the moderator, plus the attribute each `needsBuild` key waits for; code checks that it touched only the rules it makes (`ticketScopeProblems`), then the bundler's checks and the game's tests. One commit per ticket (`Ticket: W<n>`, reverted as `Reverts-Ticket: W<n>` when its night didn't go live); one claim carries the proposals' and the builds' outcomes; `needs_engine` writes a notification for Chalant's day. ## Operations

- **Quality run:** a PR that changes `src/lib/gremlin-rules.js`, `src/lib/gremlin.js`, `src/lib/drafter.ts`, `src/lib/proposals.js`, `moderator/APPLY.md` or `moderator/AUDIT.md` runs `node tests/quality/run.mjs --stage chat --grade --publish` on the mini and links the page in the PR body. The harness (`tests/quality/`) is not part of CI's model use (CI has no key); its offline tests are `node tests/quality/harness.test.mjs`. It runs against a scratch copy of the Rickshaw rules with no remote and never touches the live game.
- **Deploy:** merging to main deploys the Worker via Workers Builds. Verify on the live site after.
- **D1 migrations:** back up first, apply to preview, then prod, with the d1-migration skill (`~/chalantbot/repos/skills/d1-migration/`). Never `wrangler d1 export --remote` on a live DB.
- **Art (R2 + Workers AI):** drawings live in the private R2 bucket `promptocracy-art` (`promptocracy-art-preview` for previews), keyed by the SHA-256 of the bytes: `tmp/<sha>` as made (a bucket lifecycle rule, `tmp-30d`, deletes them after 30 days) and `art/<sha>` once saved to an entry. Only the Worker serves them, at `/<slug>/art/<sha>`. The model is the `[ai]` binding (`IMAGE_MODEL`, default `@cf/black-forest-labs/flux-2-klein-9b` since 2026-11-23, `flux-2-klein-4b` the cheaper switch, `@cf/black-forest-labs/flux-2-dev` the dearer one that draws metal as metal; `@cf/black-forest-labs/flux-1-schnell` is the fallback). **Nano Banana 2.1 is a selectable model, off by default** (`IMAGE_MODEL=gemini-nano-banana-2.1`, `NANO_MODEL` in `src/lib/art.js`): it is the one model that does not run on Workers AI, so it needs the Worker secret `GEMINI_API_KEY` (a paid-tier key: on the free tier Google may use prompts to improve its products) and draws by a plain `fetch` to `generativelanguage.googleapis.com` (`runNano`). What leaves the building is the drawing's prompt, "image only" and an aspect ratio, nothing else (`nanoRequest`; `tests/art.mjs` lists the allowed fields and fails on any other, and `GEMINI_BASE_URL`, for the tests, only takes a loopback address). A missing key, a Google error, a block or a timeout is a failed draw with its reason on `art_draws.reason` and `agent_calls.reason`, like any model error (a failure after Google answered or while it was still working is counted at the same price, since Google bills it). It is counted in the budget at `NANO_COST_MICRO` ($0.05), an ESTIMATE until it is checked against a Google bill (computed from usage: about $0.041). A drawing counts in the month's budget at its model's price (`ART_COST_BY_MODEL`, over-counted, never under). `wrangler dev` cannot start with an `[ai]` binding without a Cloudflare login, so the tests run on `wrangler.test.toml` (generated, gitignored: the same config without `[ai]`) and draw through the `ART_STUB` stand-in (`src/lib/art.js`). The daily sweep is the second cron (03:15 UTC). **A drawing's prompt is prose, subject first** (Black Forest Labs' FLUX.2 guide: the model weighs what comes first): Gremlin's words, then a short description of how they look (`claude-sonnet-5-5`, `DESCRIBE_MODEL`, is asked once per drawing, `describeFor` in `src/lib/art-check.ts`; the description is what tells a small model which member of a class to draw, so it needs a describer whose answer holds steady from one ask to the next), then ONE short per-kind block (`KIND_BLOCKS` in `src/lib/art.js`, picked by the entry's catalog kind), then a one-sentence house style, about 70-130 words in all. The creature block is the character direction; the structure, item, feature and tile blocks carry no face, eye or limb words (naming one invites it; the model has no negative prompt, so no block says "no X"). Add no example subject and no patch for one bad drawing to any block (the TRAIN and HOLDOUT subjects in `tests/fixtures/art-samples.json` are tested absent). After each drawing the same model answers that kind's question about the picture (every kind is also asked whether legible writing is on it; writing fails unless the words ask for it); only a clear yes passes, and the outcome is written on the draw (`art_draws.reason`: `check failed: ...`, `check failed again: ...` or `unchecked: ...`; empty = passed). A drawing that fails is redrawn once, NOT in the Worker that drew it (10-16 s of its 30 s): the requester's next read of the ticket starts it (`redrawFailed` in `src/lib/art.ts`, called from the ticket page; the card polls every 2 s while a drawing is out). The 11-23 hill-climb (rounds, contact sheets, verdicts) is in Chalant's `artifacts/2026-11-23-art-climb/`. **Every drawing comes on that white page; the board takes it off a creature's drawing in the browser** (`public/js/cutout.js`: near-white flood-filled from the picture's edges to transparent, so white inside the figure stays; the outline's edge is unmixed from white). Tiles and structures need no cut: they fill their own diamonds. The stored drawing keeps its page; `data-art` on the board's `image.cart-img` is still the catalog address. The tests' stub drawings are full bleed (no page), so `tests/browser-structures.py` serves one white-page drawing to exercise the cut.
